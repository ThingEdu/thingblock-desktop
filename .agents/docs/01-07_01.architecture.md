# thingblock-desktop architecture

Status: **implemented**. Describes how the Tauri shell bundles `thingblock-editor` and
`thingblock-link` into one installable app, and the contracts that must not drift. Pairs with
the link-repo docs `21-06_01.arduino-helper-design.md` (the WS protocol) and
`25-06_01.resource-serving.md` (the resource-pack HTTP surface) — this shell is a consumer of
both, not an owner.

## Why a shell repo at all

`thingblock-editor` and `thingblock-link` are released independently and already work together
in browser mode: a user runs the link helper locally, opens the editor in a browser tab, and the
editor connects to `ws://localhost:3030`. The desktop shell exists only to remove the "run a
helper, then open a browser tab" friction — it packages the same two halves behind one
double-click install, using the exact protocol that already works. It intentionally owns no
editor logic and no compile/flash logic; it is process lifecycle + bundler config.

## Two build-time inputs, resolved from sibling checkouts

`thingblock-desktop` does not vendor either sibling's source. Both are pulled in as **built
artifacts** at package time:

| Input | Source | Consumed as |
| - | - | - |
| Editor UI | `../thingblock-editor/packages/scratch-gui` | dev: webpack dev server on `:8601`. release: static `build/` dir set as Tauri's `frontendDist` |
| Link sidecar | `../thingblock-link` | `cargo build --release`, binary copied into `src-tauri/binaries/` as a Tauri `externalBin` |
| Link runtime data | `../thingblock-link/thingblock-resource/`, `../thingblock-link/arduino-cli-binaries/<host-triple>/` | copied into `src-tauri/resources/`, bundled via Tauri `resources` |

`scripts/stage-sidecar.sh` performs the link-side staging (cargo build + three copies, keyed off
`rustc -vV`'s host triple). `npm run tauri dev` / `npm run dist` run it automatically via
`beforeDevCommand` / `beforeBuildCommand` in `src-tauri/tauri.conf.json`, alongside the matching
editor dev/build script. Nothing under `src-tauri/binaries/` or `src-tauri/resources/` is
committed — both are gitignored, regenerated on every stage.

Only the host platform is staged today. Cross-platform packaging (multiple `externalBin`
targets, per-platform `arduino-cli`) is a CI concern, not something this shell does locally.

## The sidecar lifecycle (`src-tauri/src/lib.rs`)

On `setup`, the shell spawns `thingblock-link` as a Tauri sidecar (`tauri_plugin_shell`) with
three flags:

- `--port 3030` — see [Port contract](#port-contract-dont-drift) below.
- `--resource-root <path>` — resolved via `BaseDirectory::Resource` at runtime, pointing at the
  bundled `thingblock-resource/` copy.
- `--arduino-cli <path>` — same resolution, pointing at the bundled `arduino-cli` binary.

Both paths are resolved and passed explicitly rather than relying on the link's own
"next to the executable" defaults: Tauri stages sidecar binaries and resources into different
directories per platform, and without `--arduino-cli` the link falls back to its in-tree
`arduino-cli-binaries/`, which only exists on a dev checkout of the link repo — never inside a
packaged app.

The sidecar's stdout/stderr are piped into `log` (`info!`) and a `Terminated` event is logged as
`error!`. The shell does not restart the sidecar on exit — a crashed link means the editor's WS
connection drops, which is visible to the user in-app, same as if they'd killed a standalone
helper in browser mode.

## Port contract — don't drift

The editor is compiled to connect to `ws://localhost:3030`; that port is hardcoded in this shell
as `LINK_WS_PORT` (`src-tauri/src/lib.rs`) and passed to the sidecar via `--port`. This number is
a **contract with the editor**, not a local implementation detail — the editor and this shell are
different repos with independent release cadences, so silently changing the port on one side
would break the other's next release. If it ever needs to change, it changes in both repos in
lockstep, in the same PR window if at all possible.

## Trust boundary

The link owns its own tray icon and event loop as a standalone helper binary; running it as a
sidecar makes it a separate OS process from the Tauri window, which is expected, not a bug to
paper over. The webview never talks to the link directly through Tauri IPC — only through the
WebSocket, exactly as it does in browser mode. This shell validates state only at its two actual
boundaries: sidecar spawn/exit, and resolving the two `BaseDirectory::Resource` paths. Everything
else (protocol correctness, compile/flash behavior, resource-pack contents) is the link and
editor's responsibility, not re-validated here.
